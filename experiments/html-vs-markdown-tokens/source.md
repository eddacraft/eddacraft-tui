## Purpose

Implement a Rust-native json-render spec interpreter for Ratatui, enabling the
same JSON dashboard specs generated by AI (or hand-authored) to render in the
terminal TUI alongside the web dashboard.

**Why:** json-render's core value proposition is write-once, render-anywhere.
The web dashboard (DASHAI) already plans to generate constrained JSON specs from
AI prompts. Without a TUI renderer, CLI users must switch to a browser to see
custom dashboards. A Rust-side spec interpreter lets `anvil dashboard` render
the same `.anvil/dashboards/*.json` files directly in the terminal — same data,
same spec, different surface.

**Spec:** Extends [json-render brainstorm](../brainstorms/json-render-dashboard.md)
and builds on the Ratatui surface architecture from RATS and PORT modules.

## In Scope

- JSON spec parser (serde deserialisation of json-render's flat element format)
- Rust component registry mapping spec component names to eddacraft-tui widgets
- Tree renderer that walks the spec and composes Ratatui widgets
- Data context binding (resolve data paths against live `.anvil/` storage)
- Dashboard surface for `anvil dashboard` command
- Graceful degradation for components that have no TUI equivalent
- Catalogue schema validation (reject specs referencing unknown components)

## Out of Scope

- The web renderer (see DASHAI-001)
- The component catalogue definition (see DASH-003, DASHAI-002)
- AI prompt interface in the terminal (future work)
- Interactive actions (approve, suppress) from TUI dashboards (future work)
- The eddacraft-tui widget library itself (see RATS-001, complete)

## Decisions

**D-TUIDASH-001:** Component mapping strategy

- **Options:** (a) 1:1 mapping where every web component has a TUI equivalent,
  (b) Subset mapping with graceful fallbacks for unsupported components,
  (c) Abstract component model where web and TUI share trait definitions
- **Resolution:** Option (b). Not every web component translates to terminal
  (e.g., HeatMap, complex charts). Unsupported components render as a labelled
  placeholder: `[HeatMap: not available in terminal]`. This keeps the spec
  portable without blocking rendering.
- **Status:** Resolved

**D-TUIDASH-002:** Data context source

- **Options:** (a) Read `.anvil/` storage directly from Rust, (b) Shell out to
  `anvil status --json` and parse output, (c) Connect to anvil-api HTTP server
- **Resolution:** Option (a). The kernel already reads `.anvil/` storage. Reuse
  existing Rust file readers for zero-dependency data binding. Option (c) is
  available as a future enhancement for remote dashboards.
- **Status:** Resolved

**D-TUIDASH-003:** Layout engine

- **Options:** (a) Ratatui's built-in `Layout` constraints, (b) Custom flex-like
  engine, (c) CSS-grid-inspired constraint solver
- **Resolution:** Option (a). Ratatui's `Layout::horizontal` / `vertical` with
  `Constraint::Percentage`, `Min`, `Max` handles the grid-like layouts in
  dashboard specs. Complex web layouts (CSS grid) degrade to vertical stacking.
- **Status:** Resolved

## Constraints

- Spec format must match `@json-render/core` exactly — no Anvil-specific
  extensions to the spec structure (props, children, root, elements)
- Must render at 80x24 minimum terminal size (components adapt via constraints)
- Theme must reuse the palette exposed by `crates/anvil-tui` (no custom
  colours; the historic `eddacraft-tui` palette now lives there)
- Rendering a spec must not panic — malformed specs produce error UI, not crashes
- Data binding failures render as `—` (em dash), not errors

|------|------------|--------|------------|
