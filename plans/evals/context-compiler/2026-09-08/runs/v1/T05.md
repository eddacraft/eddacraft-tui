## Answer (summary)

A caller is not emitted as one result per Calls edge. In `callers_of` (`crates/anvil-graph-cache/src/call_graph.rs`), each hop deduplicates by caller node id and OR-s `heuristic` across all of that caller’s edges into the current frontier. The walk comment states a caller is heuristic if any of its calls into the frontier is an overload fan-out, so the flag is independent of frontier-visit order (`entry.1 |= heuristic`). Per-edge work still happens: `is_fan_out_call` tests one `from → to` Calls edge by counting whether the caller also has Calls edges to two or more symbols sharing the callee’s `(file, kind, name)`. That per-edge boolean is then folded onto the single `CallerResult` for that caller. The marker is conservative (a genuine multi-overload caller is also flagged; fan-out is never under-reported). It is not a graph-wide sticky bit on the calling symbol: the same caller can be heuristic for an overloaded target and not for an unambiguous one (see `fan_out_caller_is_marked_heuristic` in the same file). The flag is copied through to egress as `CallerSummary.heuristic` (`crates/anvil-gctx-types/src/lib.rs`, collected in `crates/anvil-gctx-egress/src/lib.rs`). GCALL-007 CALL-1 (`plans/archive/reviews/2026-06-17-gcall-caller-egress-privacy-review-verdict.md`) and both rustdocs say a consumer must not treat a `heuristic` caller as an exact call — overload fan-out may have over-included it. (Report-level `partial` is a separate incompleteness marker, not the exact-call honesty flag.)
