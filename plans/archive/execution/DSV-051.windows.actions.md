# DSV Sub-phase C — Windows verification checklist (operator, manual)

**Owner:** Josh (Windows machine). **Filed:** 2026-07-04 alongside the DSV-046
promotion. **Run when:** DSV-047..050 are Merged (the checklist is the manual
half of DSV-051's Windows leg; the automated half is the `rust.yml` cross
matrix + E2E cases).

Everything here needs a real Windows session — it verifies detached-process
behaviour, named-pipe transport, and console-window suppression that CI's
`windows-msvc` matrix cannot observe end-to-end.

## Setup (once)

- [ ] Build or install a current `anvil.exe`. Local build needs an MSVC
      toolchain (`aws-lc-sys` compiles C; the GNU cross toolchain is not
      enough — known local-build blocker from DSV-010).
- [ ] Unsigned dev binaries can trip Defender/SmartScreen — allow the dev
      binary or use a signed release build (known issue; signing is tracked
      separately).
- [ ] Use a throwaway `ANVIL_HOME` (e.g. `set ANVIL_HOME=%TEMP%\anvil-dsvc`)
      so the dev daemon/registry never touches the production one
      (DISTRIB-006 pattern; E2E precedent from GHCLIAUTH).
- [ ] Prepare two small disposable git worktrees (a few files each).

## 1. Headless spawn discipline (DSV-047/048)

- [ ] From worktree A: `anvil start --no-mcp`. Expect: **no console window
      flash** when the supervisor spawns the driver (`CREATE_NO_WINDOW`), no
      visible `anvil watch` terminal, exit 0.
- [ ] `{ANVIL_HOME}\runtime\save-time-drivers\` contains `<worktree-id>.json`
      (with `pid` **and** `pid_starttime` populated — the anti-spoof pair),
      the findings log `<worktree-id>.log`, and the crash-capture
      `<worktree-id>.spawn.log`.
- [ ] Task Manager (or `tasklist`): exactly one `anvil` driver child per
      registered worktree; no orphan console host.

## 2. Findings without a terminal (DSV-048)

- [ ] Save a file in worktree A containing a **planted antipattern finding**.
      The Windows daemon runs **parser-less** (tree-sitter injection is
      Unix-only), so expect the finding in the log with `Partial` coverage —
      do **not** expect `Certified` on Windows; an antipattern finding is the
      pass criterion.
- [ ] Finding line appears in `<worktree-id>.log` within one debounce window.
- [ ] Grow the log past 1 MiB (loop saves or a scripted append via planted
      findings): the **child** rotates/truncates it; the `.spawn.log` is
      untouched by findings traffic.

## 3. Status truth (DSV-049/050)

- [ ] `anvil status` and `anvil status --json` show
      `save_time_driver: attached` for worktree A over the **named pipe**
      transport (DSV-010/011 path).
- [ ] `anvil start` copy does **not** recommend a foreground `anvil watch`
      while the driver is attached; it points at `anvil intercept status` /
      the log path (DSV-050).
- [ ] Kill the driver child directly (`taskkill /PID <pid> /F`): status
      degrades to `save_time_driver: failed` (no auto-respawn at cut-line —
      that is the pinned behaviour, not a bug).

## 4. Lifecycle (DSV-047)

- [ ] `anvil workspace register <worktree B>`: second driver spawns, both
      listed `attached`; duplicate register = heartbeat, **no** duplicate
      driver process.
- [ ] Restart the daemon (`anvil intercept stop` + `anvil start --no-mcp`):
      persisted registrations reload and drivers **re-attach** (fresh PIDs in
      the JSON records; stale records overwritten).
- [ ] `anvil intercept stop`: **both** driver processes exit (bounded
      graceful terminate, then force-kill), PID records cleared, guidance
      mentions the worktrees losing drivers. Verify with `tasklist` — no
      orphaned `anvil` processes.
- [ ] Opt-out: with `ANVIL_NO_SAVE_TIME_DRIVER=1`, `anvil start --no-mcp`
      registers the worktree but spawns **no** driver; status shows
      `save_time_driver: absent`.

## 5. Evidence to capture

For the DSV-051 closure note: a `tasklist` snapshot during §4, the
`--json` status output from §3, one findings-log excerpt from §2, and the
`rust.yml` cross-matrix run URL
(`gh workflow run rust.yml --ref <branch>` — dispatchable from any machine).

## Out of scope here

Job Object containment, service-mode autostart, and code-signing are
Windows-GA hardening (explicitly out of DSV module scope); the parser-less
`Certified` gap is the known DSV-010 follow-up, not a Sub-phase C regression.
