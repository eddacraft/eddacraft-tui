# ADR-112: Anti-pattern gate severity reconciliation and generated-file handling

## Status

Accepted

## Date

2026-07-21

## Context

A beta tester wired `anvil gate` into CI on a repository using the TanStack
Router Vite plugin. The gate failed on `src/routeTree.gen.ts` — a file the
plugin generates on every `vite dev` / `vite build` and commits to the repo.
Generated files of this kind are stamped `/* eslint-disable */` and
`// @ts-nocheck` **by construction**, which trips anti-pattern rule `AP-001`
(Broad eslint-disable added). CI went red on code the user never wrote and
cannot hand-fix.

A five-persona Council decision review (kernel-maintainer, adversarial,
operations, pragmatic-lead, general reviewer) verified three findings in-repo,
all confirmed:

- **F1 — `anvil gate` promotes `warning`→blocking.** `run_check_antipattern`
  (`crates/anvil-cli/src/commands/gate.rs`) constructs its scan config with
  `severity_threshold: WarningSeverity::Warning`, overriding the engine default
  of `Error` (`crates/anvil-checks/src/antipattern/types.rs`). It is the **only**
  override site in the codebase — both MCP tool paths (`mcp/tools/gate.rs`,
  `mcp/tools/check.rs`) pass `Error`. `aggregate_scan_results` marks any finding
  at or above the threshold blocking, and `gate` maps a failed check to exit 2.
  The result: **27 of 44 rules** are `warning`-severity and become CI-blocking,
  including security-relevant ones (weak crypto MD5/SHA-1/ECB, unsafe rendering
  via `dangerouslySetInnerHTML`, and the JWT `none`-algorithm check).
- **F2 — no generated-file exclusion.** The anti-pattern scanner has no
  awareness of machine-generated files; `AP-001`'s allowlist covers only tests
  and `explain/`. (`crates/anvil-checks/src/filter.rs` ships an unused
  `ScanFilter` with `*.gen.ts` capability.)
- **F3 — anti-patterns are never baselined.** Baseline / new-edges machinery is
  SQL-drift-only; the anti-pattern check fires on every matching file regardless
  of age.

F1 contradicts the accepted **ADR-002** ("Anvil warnings do not block by
default … CI integration offers opt-in `fail-on-warnings: true`") and the
"Warnings over blocks — exit 0 by default" architecture principle. F3
contradicts "New edges only — baseline existing state". The public generated
catalogue (`docs/public/anvil/reference/rules.md`) states "a warning … does not
automatically mean a command failed", which is false on the gate surface today.

A decision is needed now because this is a beta-adoption trust problem: a
deterministic-gate product whose day-one experience is an unfixable false-positive
CI failure, on documentation that contradicts the observed behaviour.

## Decision

Split the response into an immediate mitigation and a governed reconciliation,
so the beta blocker is cleared without a silent behavioural flip.

1. **Generated-file exclusion (immediate — PR #3373).** Skip
   machine-generated files in the anti-pattern scanner core
   (`run_antipattern_check_bytes`), so `anvil check`, `anvil gate`, and the
   save-time path all stop flagging them. Detection is deliberately **orthogonal
   to** the `eslint-disable` / `@ts-nocheck` markers `AP-001` itself detects —
   keying the exemption on those would let any author silence the whole
   anti-pattern gate for a file by writing the very thing being caught. The
   signal is:
   - **path convention** — `*.gen.*` / `*.generated.*` filename infix, or a
     `generated` / `.generated` / `__generated__` path segment; and
   - **generator-attribution banner** in the leading lines — `@generated`,
     `Code generated by`, `automatically generated`, `auto-generated` (the
     GitHub Linguist `linguist-generated` convention).

   Secret detection and the other gate engines walk independently and are
   unaffected.

2. **Promote genuinely must-block rules to `error`.** The security-relevant
   rules currently misclassified as `warning` (weak crypto, unsafe rendering,
   JWT `none`) move to `error` severity, so they keep blocking after step 3.

3. **Drop the gate's `Warning` override.** Remove the
   `severity_threshold: WarningSeverity::Warning` override so warnings no longer
   block by default — restoring ADR-002 — and expose the ADR-002 `fail-on-warnings`
   opt-in for teams that want all warnings to fail. This ships with a version /
   migration note; it must **not** be a silent default flip.

4. **Defer finding-baselining.** Generalise the SQL-drift finding-baseline to the
   anti-pattern family ("new edges only") as its own ADR-gated module. This is
   the durable, spoof-resistant answer to pre-existing-violation noise and the
   real fix for F3.

Steps 2–4 are follow-up work tracked under CIB-199; this ADR records the
accepted direction. Step 1 is implemented in PR #3373 (open at the time of
writing).

## Rationale

The Council split 2–2 on whether to simply drop the `Warning` override (a bug
fix restoring the accepted ADR-002) or treat it as a load-bearing enforcement
feature that must not silently regress. The discovery of ADR-002 dissolved the
split: warnings-over-blocks is already the accepted policy, so the hardcoded
override is a drift from governance — but the objection that dropping it
silently unblocks 27 rules (including security primitives) is also valid. The
reconciling move is to make the genuinely-blocking rules `error` (so they keep
blocking on their own merit) and then honour ADR-002 for the rest, with the
`fail-on-warnings` opt-in preserving strict behaviour for teams that rely on it.

The generated-file exclusion is scoped narrowly and sequenced first because it
unblocks the entire committed-codegen class (TanStack, Prisma, GraphQL codegen,
protobuf) independent of the severity question.

### Alternatives Considered

| Option | Pros | Cons |
|--------|------|------|
| Generated-file exclusion + severity reconciliation (chosen) | Unblocks beta now; restores ADR-002; keeps security rules blocking; no silent regression | Two-step; exclusion signals are spoofable |
| Drop the `Warning` override alone | One-line, restores ADR-002 | Silently unblocks 27 rules incl. weak-crypto/JWT-`none`; no signal to operators |
| Generated-file exclusion only | Fixes the reported case | Leaves F1/F3 (warnings still block, no baseline); docs stay contradictory |
| Content-sniff `eslint-disable`+`@ts-nocheck` as the "generated" signal | Matches the exact bug input | Self-defeating: hands every author a one-line universal gate bypass |
| Baselining first | Durable "new edges only" fix | A feature (snapshot store, CI-runner persistence); too slow for the beta blocker; risks grandfathering real violations |

## Consequences

- **Positive:** Beta CI is unblocked for committed generated files across the
  codegen ecosystem. Gate behaviour realigns with ADR-002 and the architecture
  principles. Security-relevant rules keep blocking, on `error` severity that
  honestly reflects their intent.
- **Negative:** The generated-file signals (path/banner) are spoofable — a
  rename to `*.gen.ts` or a pasted banner exempts a file. This is the same
  trade-off GitHub Linguist accepts; baselining (step 4) is the spoof-resistant
  successor.
- **Risks:** Step 3 changes exit behaviour for existing `anvil gate` users who
  rely on warning-severity findings failing CI — their pipelines would go green
  silently.
- **Mitigations:** Ship step 3 with a `fail-on-warnings` opt-in and a version /
  migration note; never flip the default silently. Promote must-block rules to
  `error` (step 2) before step 3 so security coverage is preserved by severity,
  not by the override.
