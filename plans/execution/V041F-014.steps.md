# V041F-014 — Wire a database-migration runner into the deploy pipeline

## Goal

Every release that adds a SQL file under `apps/anvil-api/src/db/migrations/`
must apply on prod automatically — no operator running `psql` by hand.
v0.4.0-beta added 007–010 and the prod Pulumi Up failed with
`relation "admin_keys" does not exist`; the next tag will hit the same
trap if this lands unfixed.

## Preconditions

- Prod API stable (PR #1090 merged, `curl https://api.eddacraft.ai/api/v1/health`
  returns ok)
- Migrations 007–010 already applied to prod by hand (verified during
  v0.4.0-beta recovery — see V041F-014 work-item entry in
  `plans/modules/v041-release-followups.aps.md`)
- Neon prod connection string available via Pulumi-managed
  `DATABASE_URL` env var; staging DB available for dry-run

## Source of truth

- Work item: `plans/modules/v041-release-followups.aps.md` §V041F-014
- Migration files: `apps/anvil-api/src/db/migrations/`
- Deploy pipeline: `.github/workflows/release.yml` (Pulumi Up step)
- Target runbook: `docs/runbooks/post-deploy-smoke-check.md` +
  a new `docs/runbooks/db-migrations.md`

## Non-negotiables (from V041F-014)

1. `_migrations` tracking table records `(filename, sha256, applied_at)`
2. Lexical filename order, single transaction per file
3. Drift guard: refuse to apply if recorded sha differs from on-disk sha
   (catches retroactive edits to applied migrations)
4. Runs in CI **before** Pulumi Up so infra can rely on schema being current
5. Operator runbook for ad-hoc apply

## Steps

1. **Decide runner approach**
   - Checkpoint: written ADR or DECISION-LOG entry comparing Drizzle Kit
     (already in workspace tree), `node-pg-migrate`, and a minimal
     first-party runner; one chosen with rationale
   - Validate: `plans/decisions/DECISION-LOG.md` updated; choice referenced
     from this steps file

2. **Build the runner**
   - Checkpoint: a single command applies pending migrations against any
     `DATABASE_URL`, idempotent on re-run, exits non-zero on drift
   - Validate: `pnpm --filter @eddacraft/anvil-api migrate:apply` (or
     equivalent) succeeds locally against a fresh Postgres; second run
     reports zero pending; tampering with an applied file fails the run

3. **Add unit + integration coverage**
   - Checkpoint: tests cover happy path, drift detection, partial-apply
     resume, and lexical ordering
   - Validate: `pnpm --filter @eddacraft/anvil-api run test --run` passes
     including the new suite

4. **Wire into release workflow**
   - Checkpoint: `.github/workflows/release.yml` has a `migrate` job that
     runs against prod between `host` (artefacts published) and the
     existing Pulumi Up step; failure halts the workflow
   - Validate: workflow YAML lints; dry-run against staging via a
     `workflow_dispatch` invocation succeeds without changes

5. **Operator runbook**
   - Checkpoint: `docs/runbooks/db-migrations.md` covers ad-hoc apply,
     rollback, and the drift-guard failure mode; cross-referenced from
     `post-deploy-smoke-check.md` and from
     `docs/runbooks/neon-db-operations.md`
   - Validate: links resolve, runbook follows the existing template

6. **Backfill `_migrations` for prod**
   - Checkpoint: prod `_migrations` table contains rows for 001–010 with
     correct shas, so the first automated run after merge is a no-op
   - Validate: `SELECT count(*) FROM _migrations;` returns 10 on prod;
     dry-run of the new runner reports zero pending

7. **Mark V041F-014 Complete**
   - Checkpoint: status flipped to `Done` in
     `plans/modules/v041-release-followups.aps.md`; module count in
     `plans/index.aps.md` incremented
   - Validate: `git diff` shows the two index updates

## Exit criteria

- Next tagged release applies migrations automatically before Pulumi Up
- A retroactive edit to an applied migration file fails CI loudly
- Operator runbook lets a human do the same thing manually if CI is down

## Out of scope

- Drizzle ORM model migration (this is a SQL-only runner)
- Cross-region replication concerns (Neon handles)
- Down-migrations (forward-only, drift-guarded — matches existing pattern)
