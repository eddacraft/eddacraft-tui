## Trust boundary, v0.7.0-beta

Unchanged from `v0.6.0-beta`. The daemon and driver framework run a same-UID,
local-IPC trust model: owner-only UDS / named pipe, daemon-minted driver
identity from `SO_PEERCRED` / `GetNamedPipeClientProcessId`, manifest-driven
capability lattice, no remote / cross-UID surface, no TLS, no signed manifests.
See
[`v0.6.0-beta-security-note.md` §"Trust boundary, v1"](../archive/runbooks/v0.6.0-beta-security-note.md#trust-boundary-v1)
for the full enumeration; that section is load-bearing for this note.

## M1: IPC clients can supply lineage anchors that the daemon treats as trusted

**Surface:** `crates/anvil-intercept/src/registry.rs::register_with_lineage`
(lines `526-553`). The legacy `register` path at `:449-511` is not affected.

**What ships.** `register_with_lineage` accepts
`daemon_issued_tag: Option<&AgentTag>`, `pid: u32`, and `pid_starttime: u64` as
parameters and seeds them into the registry's
`(pid, pid_starttime) -> session id` lineage index at `:548-550`. The contract
assumes the daemon-side call site has already minted the tag and read
`pid_starttime` from the OS — but the function signature itself does not enforce
that origin. An IPC frame that reaches this call path with attacker-supplied
lineage values would be admitted into the trusted lineage index and returned by
`lookup_tag_for_lineage` on subsequent cross-checks. This is the trust-boundary
issue tracked as DeepSec
[#1674](https://github.com/eddacraft/anvil-001/issues/1674) ("IPC clients can
mint trusted lineage tags").

**Why this matters.** The MLP2-025 spoof cross-check (live since PR #1608)
relies on `lookup_tag_for_lineage` being authoritative — if an untrusted caller
can seed the index with a lineage anchor matching its own PID, it can pass the
cross-check by impersonating its own "registered" lineage rather than by holding
the daemon-minted tag. The same-UID trust boundary (§ above) still applies —
only same-UID peers can reach the IPC surface in the first place — but the
cross-check is the second layer that distinguishes caller-supplied claims from
daemon-derived trust, and that second layer is weakened wherever
`register_with_lineage` is reachable from the wire without the daemon
re-deriving lineage from `SO_PEERCRED` / `/proc/PID/stat`.

**Operator framing.** Treat `degraded:spoofed-attribution` fence reasons in
v0.7.0-beta as the **first-line** defence rather than the only one. The cross-
check still rejects out-of-lineage PID-reuse spoofs against the public
`register` path. Same-UID code paths that talk straight to
`register_with_lineage` — none ship in the v0.7.0-beta binary, but any
operator-installed driver or MCP client running under the daemon's UID could in
principle reach it — are inside the same-UID trust zone by definition and the
operator's controls against that exposure are `~/.config/anvil/drivers.allow`
and the manifest allowlist already documented in `v0.6.0-beta-security-note.md`
§H1.

**What an operator MUST do.** Nothing additional in v0.7.0-beta. The default
manifest-driven capability lattice (`v0.6.0-beta` §"What v1 enforces") is
already the gate: drivers cannot reach the lineage register without being on the
allowlist and passing the existing manifest workspace-root check. Do not enable
`telemetry.allow_cross_session` (default `false`,
`crates/anvil-intercept/src/config.rs:239`) — that flag remains the documented
visibility boundary. Post-MLP2-071 Phase 1 the daemon now flows the flag through
to the `Fanout` instance constructed at startup and keys the redaction primitive
under a per-startup HMAC salt (closes `v0.6.0-beta-security-note.md` §H2 on the
redaction-primitive half); the operator-visible end-to-end behaviour still waits
on the production producer + IPC subscriber surface (Phase 2 — see CHANGELOG
"Known gaps" + INTD-015 follow-up
[#1722](https://github.com/eddacraft/anvil-001/issues/1722)).

**What is tracked for the next tag.** Move lineage derivation off the wire and
into the daemon's IPC handler. Tracked as MLP2-070 (lineage anchor
daemon-derivation hardening) in
[`plans/modules/multilayer-protection-v2.aps.md`](../../plans/modules/multilayer-protection-v2.aps.md);
parent multi-session work shipped as MLP-014 (Complete, see
[`plans/archive/modules/multilayer-protection.aps.md`](../../plans/archive/modules/multilayer-protection.aps.md)
§"MLP-014: Multi-session-per-worktree + per-task fence isolation"). The fix
re-reads `pid` and `pid_starttime` from the connected peer's `SO_PEERCRED` /
`GetNamedPipeClientProcessId` and `/proc/PID/stat` rather than trusting the
request body — same shape as the per-startup HMAC salt fix tracked for
`v0.6.0-beta` §H2.

---

## What's NOT widened in this release

Unchanged from `v0.6.0-beta`. No remote / cross-UID surface. No TLS. No signed
manifests. The v1 trust boundary is local, same-UID, and manifest-driven — the
item above is MEDIUM (not HIGH) because it sits one layer inside that boundary
and is gated by the existing manifest allowlist that v0.6.0-beta documented.
