This is the operator-facing runbook for cutting the `v0.7.0-beta` tag. The
audience is the release engineer executing the tag, not a contributor reading
the codebase. The shape mirrors `v0.6.0-beta` — what ships, what the operator
should expect, where recovery lives — refreshed for the daemon-working slate.
Two pre-flight gates (§1 clawpatch scan, §2 council review) sit ahead of the
nine tag-time gates carried forward from prior tags; three post-tag steps (§13
APS reconciliation, §14 release-record fill-in, §15 CHANGELOG version bump)
finalise the published-state artefacts before the tag is announced.

Companion: the six N4 runbooks (adoption, witness-chain, hook-coexistence,
air-gap, `anvil-run`, migration) are the **user-facing** documentation gate.
This runbook is the **operator-facing** procedure. The Upstream / Downstream
table above is the source-of-truth index for both lanes.

## 3. Tag-time hard gate: protection claim renders on every surface

**What ships.** `v0.7.0-beta` is the daemon-working release. The tag-time claim
is verifiable from code state alone — no Boring Week prerequisite, no post-tag
updates required. The hard gate is the closed-set protection-claim vocabulary
(MLP-009) rendered honestly on every shipping surface (MLP2-048,
MLP2-051a..-051c, MLP2-051e):

| Surface                            | Source of truth                                                                               |
| ---------------------------------- | --------------------------------------------------------------------------------------------- |
| `anvil status --json`              | `schemas/anvil-status.v1.json` nested `claim` field                                           |
| `anvil doctor --json`              | `protection_claim` field — same `ProtectionClaim` content, byte-identical to status's `claim` |
| MCP shim `validate_write` response | Typed `Option<ProtectionClaim>` gated on `DaemonStatus::Available`                            |
| TS driver-client mirror            | `ProtectionClaim` parity-tested against the Rust fixture                                      |
| GH Action check render (`-051d`)   | **Blocked** on the Marketplace publishing track — carved out of the gate per spec             |

Note: `anvil status --json` exposes the claim under the top-level `claim` key
while `anvil doctor --json` uses `protection_claim`. The contents are
byte-identical when serialised; only the wrapping key differs.

**Pre-flight check.** Run this sequence in a freshly-activated repo on the
candidate SHA:

```bash
# 1. Activate and confirm a Full claim on the CLI surface.
#    --verify is the activation diagnostic path; the protection claim is on
#    the plain `anvil status --json` flow under the `.claim` key.
anvil start
anvil status --json | jq '.claim.worktree_state'  # → "full"

# 2. Confirm the doctor surface carries the byte-identical content under its
#    own wrapping key.
diff <(anvil status --json | jq '.claim') \
     <(anvil doctor --json | jq '.protection_claim')

# 3. Confirm the MCP shim emits the claim.
#    Either the headless RMCP smoke or a manual MCP client run is sufficient.
pnpm --filter @eddacraft/anvil-e2e test:smoke

# 4. Confirm the TS driver-client mirror builds and parity tests pass.
pnpm --filter @eddacraft/anvil-driver-client test
```

All four must report a `full` `worktree_state` or the byte-identical claim shape
before the tag is cut. Any `Degraded` / `PreWriteDaemon` / `NotWired` surface
routes to the relevant N4 runbook for the recovery procedure.

## 4. Foreground daemon is still the only supported launch mode

**Carry-forward from `v0.6.0-beta` §1.** The release council validated only
foreground daemon launches for `v0.6.0-beta`, and the same constraint holds in
`v0.7.0-beta`. Operators running under a system service manager (systemd,
launchd) should run the daemon foreground under the manager's supervision rather
than double-backgrounding.

**Start path:**

```bash
anvil intercept start --foreground
```

**PID file resolution** is unchanged (`default_pid_file_path` in
`crates/anvil-intercept/src/lib.rs`):

- `$XDG_RUNTIME_DIR/anvil/intercept.pid` if set.
- `$HOME/.local/state/anvil/intercept.pid` otherwise (Linux / macOS).
- `%LOCALAPPDATA%\anvil\intercept.pid` on Windows.

**Stuck-daemon kill order** is unchanged: SIGTERM, wait 10 s, then SIGKILL
paired with the data-directory cleanup (the cleanup is still mandatory after
SIGKILL — a stale socket / PID file blocks the next start). See the
`v0.6.0-beta` runbook §1 (carry-forward from `v0.6.0-beta`) for the exact
sequence; nothing about it changed.

## 5. Fence recovery is now a CLI subcommand

**What changed from `v0.6.0-beta`.** The hard-reset path
(`rm -rf $XDG_DATA_HOME/anvil`) is still available but no longer the **only**
recovery for a fenced worktree. RCLI3-017b shipped the per-fence unblock CLI
surface; MLP2-026 added the cascade-clearing affordance.

```bash
# Clear a single fenced worktree (idempotent on already-unfenced state).
anvil intercept unblock --worktree /path/to/worktree

# Clear every fenced worktree in one call.
anvil intercept unblock --all

# Preview what would be cleared without modifying daemon state.
anvil intercept unblock --worktree /path/to/worktree --dry-run

# Clear a degraded:fence-cascade state (distinct from per-fence unblock).
anvil intercept unblock /path/to/worktree --acknowledge-cascade
```

The legacy positional form (`anvil intercept unblock <WORKTREE>` without a flag)
is reserved for the MLP2-026 cascade path and **requires**
`--acknowledge-cascade` — operators who try to use it for per-fence unblock will
get a refusal pointing at the `--worktree` form.

**When the CLI is not enough.** Fence persistence is unchanged — fences survive
daemon restart, process crash, machine reboot, and any combination. If the
daemon refuses to start because fence state on disk is corrupted (not just
engaged), the hard-reset path from the `v0.6.0-beta` runbook §3 (carry-forward
from `v0.6.0-beta`) is still the documented recovery:

```bash
# Stop the daemon (Ctrl-C in its terminal, or SIGTERM by PID), then:
rm -rf "${XDG_DATA_HOME:-$HOME/.local/share}/anvil"
anvil intercept start --foreground
```

This destroys **all** fence state for the user. Capture any fence-file contents
needed for incident triage before removal.

## 6. Witness-chain audit must be clean on the candidate SHA

**What ships.** `v0.7.0-beta` is the first release where the witness chain is
load-bearing — pre-push refuses on chain breaks, the L5 audit runs nightly, and
the protection-claim contract reads chain state to decide what to render. The
tag cannot ship with a broken chain on the candidate branch.

**Pre-flight check:**

```bash
anvil audit-chain --threshold 1 --branch main --json | jq '.degraded'
# expect: false
```

A `degraded: true` response means drift met or exceeded the `--threshold` (here
`1`). Resolve before tag:

- If the report lists **Unwitnessed commits** — route to the re-witness path in
  the [witness-chain runbook](anvil-witness-chain.md) §"Failure mode 5".
- If the report lists a **Chain integrity FAILED** anchor — route to the revert
  path (single-commit only) in the same section.

**Multi-branch adoption corner case.** If `v0.7.0-beta` is the first release to
activate Anvil on more than one long-lived branch in the release repo, an
OrphanMerge on first cross-branch merge is expected and documented. See the
[migration note's "Multi-branch adoption" section](../archive/runbooks/v0.6.x-to-v0.7.0-beta-migration.md#multi-branch-adoption-enterprise-monorepo)
for the rollout sequence. Do not cut the tag on a chain with an active
OrphanMerge.

## 7. Hook coexistence install/uninstall round-trip

**What ships.** ADOPT-001 added hook coexistence with lefthook, husky, and
pre-commit-framework. The pre-tag check confirms the install and uninstall paths
are byte-stable on representative fixtures.

**Pre-flight check.** Against a fresh fixture for each host hook manager:

```bash
cd <fixture>
anvil hooks install --config       # confirm coexistence report is clean
git diff --quiet                   # canonical-form diff is acceptable on Husky
anvil hooks uninstall --config
git diff --quiet                   # round-trip must match the install diff
```

Acceptable diffs after uninstall (documented in the
[hook coexistence runbook](anvil-hook-coexistence.md) round-trip guarantee):

- Husky files with non-canonical trailing whitespace are canonicalised
  (cosmetic).
- User-added Lefthook `extends:` entries and pre-commit-framework `repos:`
  entries are **not** auto-removed — these are user-owned.

Any other diff is a regression and blocks the tag.

## 8. `anvil-run` smoke

**What ships.** INTL-001..-009 shipped via PR #1528. The
[`anvil-run` manpage](anvil-run.md) is the operator reference; the release
pre-flight just confirms the wrapped-launch ingress is alive on the candidate.

```bash
# Wrap a no-op and confirm the launcher returns the child's exit code.
anvil-run --tool claude-code -- true
echo $?  # 0

# Confirm refusal banners format correctly under a fenced worktree
# (expect exit 75 + stderr banner).
anvil-run --tool claude-code --dry-run -- true
```

**Trust-model anchor.** `ANVIL_TASK_ID` / `ANVIL_AGENT_TAG` are advisory hints,
not authenticated identity. The daemon authenticates against the witness chain
(ADR-037 §D-2) and `validate_at_l4` (ADR-037 §D-5). See the manpage's TRUST
MODEL and SECURITY CONSIDERATIONS sections for the full statement.

## 9. macOS interrupt is still fence-first

**Carry-forward from `v0.6.0-beta` §4.** The `current_process_start_time` helper
still returns `None` on macOS, so every interrupt decision falls through to the
fence-on-uncertainty path per AD-7. Operators on macOS should expect:

- Interrupt decisions trigger fences, not signal ladders.
- `anvil intercept status` shows the fenced worktree.
- Recovery is now `anvil intercept unblock --worktree <path>` (no longer the
  hard-reset path for the normal case — see §5 above).
- Fence telemetry shows `FenceReason::SignalDeliveryFailed` or equivalent
  disproportionately on macOS.

The fix lives outside this release (helper implementation work on
`current_process_start_time`).

## 13. APS reconciliation pass

**What it is.** Every APS item enumerated in `plans/releases/v0.7.0-beta.md`
under `aps.items[]` advances its status from `Merged` → `Released/Shipped` once
the tag is published and post-publish verification (§3..§11 + tag.sh exit 0) has
succeeded. This is the canonical shipped-state promotion that makes the items
eligible for archival.

**Why it gates "tag complete."** A `Merged` status means the code reached
`main`; `Released/Shipped` means the code reached users via a published tag. APS
reconciliation drift (items stuck at `Merged` after tag) breaks the
index-vs-released-evidence join that release records exist to provide.

**Tooling.** `scripts/aps-cleanup.sh --advance-released` (#1715) drives this
from the release record — no manual `awk`/`perl` walk. It is the only
`aps-cleanup.sh` mode that writes module statuses (the default run is still a
passive reporter). It delegates to `scripts/aps/advance-released.mjs`, which
locates each item by **heading search across all module files** (active _and_
archived, `###` and `####`), so it does not depend on the record's `module`
field matching a filename and does not skip nested-group modules — the two ways
the old manual walk silently MISSed items.

**Run it.** One invocation; preview with `--dry-run` first:

```bash
SHA=$(git rev-parse HEAD)
DATE=$(date -u +%Y-%m-%d)

# Preview — writes nothing; lists ADVANCED / SKIP / MISS:
scripts/aps-cleanup.sh --advance-released \
  --release-record plans/releases/v0.7.0-beta.md \
  --tag v0.7.0-beta --sha "$SHA" --date "$DATE" --dry-run

# Apply:
scripts/aps-cleanup.sh --advance-released \
  --release-record plans/releases/v0.7.0-beta.md \
  --tag v0.7.0-beta --sha "$SHA" --date "$DATE"
```

Each `Merged` item in the record's `aps.items[]` becomes
`Released/Shipped via <tag> (<8char-sha> · <date>)`. Items already
`Released/Shipped` or `Complete` are SKIPped, so re-runs are idempotent. The
command exits non-zero if any item MISSes (see Failure modes). `Merged` and
`Released/Shipped` are both "done", so module `N/M` counters do not change;
confirm no drift afterwards:

```bash
node scripts/aps/index-counts.mjs --check
node scripts/aps/drift-check.mjs
```

**Pass criteria.**

- The command exits 0 — every record item was ADVANCED or idempotently SKIPped.
- A spot grep confirms the advance, e.g.
  `grep -rl "Released/Shipped via v0.7.0-beta" plans/modules/`.
- `index-counts.mjs --check` and `drift-check.mjs` report no drift.

**Failure modes.** Each prints a `MISS: <id>` line and forces a non-zero exit —
no silent skips:

- **Heading not found in any module** — the record lists an item that exists in
  no active or archived module. Likely a missed back-fill or a stale record; add
  the item to a module or remove it from `aps.items[]`, then re-run.
- **Status is not `Merged`** (e.g. still `In Progress`/`Proposed`) — the record
  claims the item shipped but it never reached `Merged`. Fix the item's status
  (or the record) before re-running.
- **`Merged` item in an archived module** — anomalous (archived items should be
  `Complete`/`Released`); the script refuses to rewrite a frozen archive file.
  Investigate the archive entry.

**What to capture.** A single commit covering all status advances — do not split
per module. Commit message:
`chore(aps): reconcile v0.7.0-beta items to Released/Shipped`.

The `--advance-released` mode and its fixture tests
(`scripts/aps/_test/advance-released.test.sh`) close the tooling gap formerly
tracked as [GH #1715](https://github.com/eddacraft/anvil-001/issues/1715).

## 14. Release-record fill-in

**What it is.** Advance `plans/releases/v0.7.0-beta.md` from
`lifecycleState: "candidate"` to `lifecycleState: "published"` and populate
every null field with the tag-time data. The pre-tag record was written against
an unknown SHA; the post-tag record locks the shipped state.

**Why it gates "tag complete."** A `candidate` record is not consumable for APS
reconciliation. Until `lifecycleState: "published"` is set, the items advanced
in §13 have no joined release evidence.

**Fields to populate.**

```jsonc
{
  "lifecycleState": "published",
  "source": {
    "commitSha": "<full sha of v0.7.0-beta tag>",
    "tag": "v0.7.0-beta"
  },
  "artifacts": [
    /* full asset list from cargo-dist output — per-platform archive
       URLs, sha256s, sizeBytes; installer scripts; checksum file;
       source tarball; dist-manifest.json */
  ],
  "releases": {
    "private": { "url": "<private repo release URL>" },
    "public":  { "url": "<public repo release URL>" }
  },
  "verification": {
    "verifiedAt": "<ISO-8601 timestamp of post-publish verify>",
    "ciRunUrl":  "<URL of the green CI run for the candidate SHA>",
    "checks": [
      /* every check that gated the tag — clawpatch scan from §1,
         council review from §2, protection-claim parity from §3,
         witness-chain audit from §6, hook round-trip from §7,
         anvil-run smoke from §8, air-gap from §11, cargo-dist
         build matrix, install smoke */
    ],
    "installSmoke": {
      "status": "pass",
      "command": "curl -fsSL https://install.eddacraft.ai | sh"
    }
  },
  "trackingIssue": {
    "number": <issue number>,
    "url": "<URL of the tag tracking issue>"
  },
  "aps": { "reconciledAt": "<ISO-8601 of §13 commit>" }
}
```

**Pass criteria.**

- `lifecycleState: "published"`.
- All previously-null fields populated.
- File validates against the release-record schema at
  `plans/specs/2026-05-10-release-record-schema.md`.
- Asset SHAs match `sha256.sum` byte-for-byte.

**Failure modes.**

- Asset list incomplete: cargo-dist run did not finish or some platforms failed.
  Re-run the publish workflow; do not hand-curate the asset list.
- `verification.checks[]` missing the council review from §2: the council review
  file at `plans/reviews/release-council/` is the canonical evidence — its URL
  goes in the checks entry. A release record without a council review entry is
  incomplete.

**What to capture.** Commit the filled-in record. Commit message:
`docs(release): publish v0.7.0-beta record + reconcile APS`. This is typically
the same commit as §13; the cleanup script can produce both edits in one pass.

## 15. CHANGELOG version bump

**What it is.** Convert the `## [Unreleased]` section to
`## [0.7.0-beta] — <YYYY-MM-DD> — Daemon-Working End-to-End Protection` and open
a fresh empty `## [Unreleased]` at the top of the file. Add an `### Upgrade`
subsection with the same shape as `v0.6.3-beta` (Homebrew / curl-installer /
WinGet / Scoop / direct).

**Why it gates "tag complete."** The migration note's upstream link points at
the versioned section; the link is invalid until this bump happens. The
CHANGELOG is also the canonical customer-facing release notes — the GitHub
Release body should quote it.

**Edit shape.**

```diff
 ## [Unreleased]

+## [0.7.0-beta] — <YYYY-MM-DD> — Daemon-Working End-to-End Protection
+
 ### Added
 ...
 ### Fixed
 - **Local-noise ignore policy now covers every surface.** ...

+### Upgrade
+
+- Homebrew: `brew upgrade eddacraft/tap/anvil`.
+- curl installer: rerun the installer.
+- WinGet / Scoop / direct download: pick up the new release as normal.
+- Migration questions: see [v0.6.x → v0.7.0-beta migration note](docs/archive/runbooks/v0.6.x-to-v0.7.0-beta-migration.md).
+
 ## [0.6.3-beta] — 2026-05-15 — Beta Watch UX + Uninstall Hotfix
```

The new empty `## [Unreleased]` at the top is the seed for the next tag's
harvest.

**Pass criteria.**

- `[0.7.0-beta]` section present with the published date.
- Empty `[Unreleased]` section above it.
- `### Upgrade` subsection covers every supported install path.
- `oxfmt --check CHANGELOG.md` clean.
- Migration note's upstream link to `[0.7.0-beta]` resolves (the slug now exists
  in the file).

**Failure modes.**

- Slug mismatch: the migration note may reference a slug that oxfmt generates
  differently. Re-run the migration note's slug check after the bump and update
  the link if needed.
- Header order: the `## [Unreleased]` line must precede `## [0.7.0-beta]` —
  readers expect newest-first.

**What to capture.** Commit on `main`. Commit message:
`docs(changelog): version-bump [Unreleased] → [0.7.0-beta]`. Push; the GitHub
Release announcement quotes the published section directly.

## Edge cases and known gaps

**Daemon-version skew is still not a v1 concern.** `v0.7.0-beta` remains a
single-version daemon — no rolling upgrade story, no peer compatibility matrix,
no driver-version negotiation that survives a daemon restart. The witness chain
shape is forward-compatible (older binaries read newer lines without emitting
the extensions), but a production deployment should still pin one version per
user.

**Marketplace publishing track is carved out.** MLP2-042..-045 + MLP2-051d (GH
Action check render) are blocked on the licensing / pricing model lock and
remain deferred — not blockers for the daemon-working claim. The release notes
ride them under a Marketplace follow-up section, not under the
protection-surface claim.

**Three Wave 0 follow-ups remain open as GitHub issues:**

- [#1705](https://github.com/eddacraft/anvil-001/issues/1705) — Extend
  `air_gapped.rs` to cover the new surfaces. **Not tag-blocking.**
- [#1707](https://github.com/eddacraft/anvil-001/issues/1707) —
