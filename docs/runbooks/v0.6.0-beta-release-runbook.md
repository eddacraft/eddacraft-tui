# v0.6.0-beta — operator runbook

**Date:** 2026-05-07 **Tag:** `v0.6.0-beta` **Owner:** Release council
**Status:** Operator-facing runbook for the `v0.6.0-beta` cut

This runbook documents the five operational items the release council's
operations-reviewer lens surfaced during the `v0.6.0-beta` review. Each item
names the file and line range an operator can audit, the supported workaround
for v1, and the tracking handle (where one exists) for the follow-up. The
intended audience is the operator running the daemon in front of a developer or
a customer demo, not a contributor reading the codebase.

Companion document:
[`v0.6.0-beta-security-note.md`](./v0.6.0-beta-security-note.md) covers the
trust boundary and the four HIGH security trade-offs the same review surfaced.
Read that note for the framing of what same-UID local IPC buys and does not buy
in v1.

---

## 1. Foreground daemon is the only supported launch mode for v1

**What ships.** The runbook-recommended path to start the daemon is
`anvil intercept start --foreground`. Output goes to the operator's terminal;
the daemon stays attached to the controlling TTY. This is the mode the RTAI demo
runbook calls out at `plans/specs/2026-04-26-rtai-demo-runbook.md` §4.1 as the
way to surface PID and startup errors directly to the operator rather than
burying them in a system log.

**PID file location.** `default_pid_file_path` in
`crates/anvil-intercept/src/lib.rs:278-294` resolves the PID file in this order:

- `$XDG_RUNTIME_DIR/anvil/intercept.pid` if `XDG_RUNTIME_DIR` is set.
- `$HOME/.local/state/anvil/intercept.pid` otherwise (Linux / macOS).
- `%LOCALAPPDATA%\anvil\intercept.pid` on Windows.

The foreground and background launch paths share the same PID file, so a second
instance (foreground or otherwise) refuses to start while the first is alive.
That is the intended invariant — the daemon is per-user singleton — but it is
also the most common reason a `--foreground` start fails: a stale PID file from
a prior crash or a backgrounded instance the operator forgot about.

**Stuck daemon kill order.** When the daemon is unresponsive to
`anvil intercept stop` and the operator must intervene manually:

1. `kill <PID>` (SIGTERM) first. The daemon's shutdown handler flushes fence
   state and unbinds the IPC listener cleanly.
2. Wait 10 seconds. If the PID is gone, recovery is complete.
3. `kill -9 <PID>` (SIGKILL) only if SIGTERM did not unwind. Then run the hard
   reset path from `2026-04-26-rtai-demo-runbook.md` §3.2:
   `rm -rf ${XDG_RUNTIME_DIR:-$HOME/.local/state}/anvil` to clear the socket and
   PID file, and `rm -rf ${XDG_DATA_HOME:-$HOME/.local/share}/anvil` if fence
   state has also gone bad.

A SIGKILL without the directory cleanup leaves a stale socket / PID file the
next start will refuse on. Always pair the SIGKILL with the cleanup.

**Background launch is not a v1 surface.** The daemon binary supports the
mechanics of a backgrounded launch (it is what the PID file guards against), but
`anvil intercept start --foreground` is the only mode the release council
validated for `v0.6.0-beta`. Operators running the daemon under a system service
manager (systemd, launchd) should run it in foreground mode under the manager's
supervision rather than double-backgrounding.

## 2. `anvil intercept status` is Unix-only in this release

**What ships.** On Unix targets, `crates/anvil-cli/src/commands/intercept.rs`
queries the daemon over the UDS IPC and renders the status snapshot per the RTAI
demo runbook §1.5 contract. On Windows, the same command hard-fails with a
structured error at `crates/anvil-cli/src/commands/intercept.rs:161-167`:

```
`anvil intercept status` over the daemon IPC is only supported on Unix
in this build; Windows named-pipe client support lands with the DRVR-001
client port
```

The error is intentional, not a bug. The named-pipe client port is a DRVR-001
(Wave 2) deliverable; the v1 cut ships the listener side of the named pipe
(`crates/anvil-intercept-win32`) but not the CLI client side.

**Operator workaround on Windows — but read the bound below first.** On Unix,
`anvil_validate_write` MCP tool responses include a daemon-reachability signal:
`correlation.daemonStatus` (camelCase, nested under the `correlation` object)
with one of three string values — `available`, `not-wired`, or `unavailable`.
The serialisation site is
`crates/anvil-cli/src/mcp/tools/validate_write.rs:325-333` (the `correlation`
envelope build); the string forms come from `DaemonStatus::as_str` at
`crates/anvil-cli/src/mcp/validation.rs:69-78`. The field tells the operator
whether the daemon path is alive — it is **not** the full uptime / sessions /
fences / latency rollup the Unix CLI prints. **On Windows in `v0.6.0-beta`, this
field is always `not-wired`** because the daemon validation client is gated
`#[cfg(unix)]` (see `crates/anvil-cli/src/mcp/validation.rs:142-148`, where the
`cfg(not(unix))` arm of `LocalDaemonValidationClient::validate_pre_write`
returns `DaemonValidationOutcome::Unavailable` unconditionally, which the caller
maps to `DaemonStatus::NotWired` at
`crates/anvil-cli/src/mcp/validation.rs:371-382`). It therefore cannot
distinguish daemon-up from daemon-down on Windows today. There is no MCP-side
workaround for the Windows status query in this release; an MCP-side fix would
need to wire the MCP validation client through the Windows named-pipe client
that ships alongside `chore/windows-status`.

For uptime / fence-count / latency on Windows, no v1 surface exists; operators
must wait for the `chore/windows-status` follow-up to land the named-pipe CLI
client.

If the operator needs to exercise the MCP launch shim end-to-end on Windows
today, the headless RMCP smoke (`pnpm --filter @eddacraft/anvil-e2e test:smoke`,
defined at `apps/e2e/package.json:13`) drives the same code path via vitest's
standard reporter, but it does not surface the per-session / per-fence detail of
the Unix status command and is a developer/CI artefact rather than an operator
surface.

**Tracked for follow-up.** `chore/windows-status` covers the Windows CLI client
port. It rides on DRVR-001 client work; the v0.6.0-beta cut does not block on it
because the headline path for v1 (Linux + macOS via Unix domain sockets) ships
the full `anvil intercept status` rollup and the Windows status gap is
documented above as accepted v1 scope rather than a regression.

## 3. Fence state survives daemon restart and never auto-clears

**What ships.** Fence persistence is owned by INTD-005. When the daemon applies
a fence (per AD-7's fence-on-failure invariant, see
`crates/anvil-intercept/src/interrupt.rs:26-43`), the fence is recorded to disk
in the data directory (`$XDG_DATA_HOME/anvil` or platform equivalent) and the
worktree is marked fenced. The daemon reads the fence state on startup and
re-fences each affected worktree before serving any IPC request.

**Restart does NOT release fences.** This is the most common operator
expectation gap in the v1 cut. A fenced worktree stays fenced across:

- `anvil intercept stop` followed by `anvil intercept start --foreground`.
- Daemon process crash and re-launch.
- Machine reboot (the fence file persists in the data directory).
- Any combination of the above.

The release council's operations-reviewer flagged this because operators who hit
a fenced session during a demo or a workflow rehearsal often reach for "restart
the daemon" first. That path does not work for fences by design — the fence is
meant to survive ungraceful daemon shutdown so an interrupted enforcement
decision is not silently undone by a daemon crash.

**The right command is `unblock`, not restart.** When
`anvil intercept status --json` shows `fenced: true` for a session, the recovery
is:

```bash
anvil intercept unblock --worktree "<path>"
```

(or `anvil intercept unblock --all` for a full release if multiple worktrees are
stuck). The `unblock` surface is owned by INTD-007 (data path) and the CLI
front-end documented in `plans/specs/2026-04-26-rtai-demo-runbook.md` §3.1.

**When `unblock` fails.** If `unblock` itself returns an error, the fence file
is the source of truth — see the hard-reset path in
`2026-04-26-rtai-demo-runbook.md` §3.2
(`rm -rf ${XDG_DATA_HOME:-$HOME/.local/share}/anvil`). That path destroys _all_
fence state for the user, including fences the operator wanted to preserve, so
prefer `unblock --all` first and fall back to the file removal only when the CLI
cannot reach the daemon.

## 4. macOS interrupt ladder always fences on missing start time

**What ships.** The `current_process_start_time` helper in
`crates/anvil-intercept/src/interrupt.rs:407-432` is implemented for Linux only.
On macOS the helper returns `None` unconditionally
(`crates/anvil-intercept/src/interrupt.rs:419-431` documents this explicitly:
"macOS: `proc_pidinfo` returns start time in `pbi_start_tvsec` ... this branch
returns `None` so the PID-reuse defence falls through to the conservative 'treat
as mismatch' path on macOS until the helper gains a macOS branch").

**What that means in practice.** Every interrupt decision on macOS that needs to
verify the leader's start time falls into the `Err(reason)` arm of
`verify_leader`. AD-7 (`crates/anvil-intercept/src/interrupt.rs:26-43`) forces a
fence on that arm. The macOS interrupt ladder is therefore **fence-first** in
v1: instead of running the SIGINT → SIGTERM → SIGKILL ladder, the daemon fences
the worktree and surfaces the failure to the operator.

**Expected v1 behaviour.** Operators on macOS should expect:

- Interrupt decisions trigger fences, not signal ladders, in any case where the
  registry recorded a non-zero `started_at_unix`.
- The fenced worktree appears in `anvil intercept status` with `fenced: true`.
- Recovery is the same as item 3 above: `anvil intercept unblock --worktree`.
  Restart does not help.
- Fence telemetry on macOS will show `FenceReason::SignalDeliveryFailed` or
  equivalent disproportionately compared to a Linux deployment of the same
  workload.

**If it bites a real workflow.** Manual unblock first, then file a bug
referencing the `current_process_start_time` macOS-branch gap. The fix is
implementation work on the helper; tracked outside this release.

## 5. Windows CI regressions on `dev` branches are silent until `main` sync

**What ships.** The Windows cross-compile job in `.github/workflows/rust.yml` is
gated by:

```yaml
if: >-
  (github.event_name == 'push' && github.ref == 'refs/heads/main') ||
  (github.event_name == 'pull_request' && github.base_ref == 'main')
```

This is documented end-to-end in
[`docs/runbooks/intd-012-windows-evidence.md`](./intd-012-windows-evidence.md).
The trade-off is deliberate: a Windows runner per dev push is a budget the
maintainers chose not to pay before the A2 release. The cost is that **any
Windows-only regression introduced on a `dev` branch is invisible in CI until
the dev → main sync runs the cross-compile matrix**.

**Operator implication for `v0.6.0-beta`.** If a Windows operator reports a bug
against a build cut from a `dev`-branch artefact (an internal pre-tag artefact,
a side-by-side dry-run binary, or a contributor branch), the CI green that ships
with the build does **not** mean Windows was tested for that change. The
contributor or release engineer must manually re-run the Windows matrix before
the bug report is rooted at the operator's environment rather than the build.

**Workaround before root-causing.** Before triaging a Windows bug from a
dev-build, run one of:

1. `cargo test --workspace --target x86_64-pc-windows-msvc -- --test-threads=1`
   locally on a Windows host (or via the release engineer's Windows VM). This
   matches the cross-compile job's smoke-test step at
   `.github/workflows/rust.yml:423` exactly; the `--test-threads=1` flag is
   load-bearing for tests that contend on shared per-user state.
2. Push a Rust-touching commit to the `dev` branch and let the post-#1325
   trigger gate fire the cross-compile job. The workflow file does **not**
   declare `on: workflow_dispatch` (see `.github/workflows/rust.yml:3-30`), so
   the GitHub Actions UI does not currently expose a manual-dispatch button for
   `rust.yml`; the only way to force a Windows run today is to re-trigger via
   push or PR. Widening the trigger surface (either `workflow_dispatch` or a
   broader `if:` on the cross-compile job) is the `chore/windows-status`
   follow-up's call.

Only after one of those produces a clean signal should the bug report move
forward as "Anvil bug" rather than "untested target". A failing cross-compile
run reframes the report as a Windows regression to fix before sync; a passing
run focuses triage on the operator's environment.

**Tracked for follow-up.** `chore/windows-status` (same handle as item 2) covers
expanding the Windows CI trigger. The decision to expand or not is a
maintainer-policy question, not a v0.6.0-beta blocker — the A2-cut Windows
surface is currently green on every release-path run (see
`intd-012-windows-evidence.md`'s recent runs table).

## Edge cases and known gaps

**See the security note for the four HIGH trade-offs.**
[`v0.6.0-beta-security-note.md`](./v0.6.0-beta-security-note.md) documents the
four HIGH security items the release council surfaced: allowlist file mode not
verified before read (H1), unsalted SHA-256 hash for cross-session redaction
(H2), spec-only `§4.4` redaction filter for non-`validate_write` MCP tools (H3),
and the Linux-microsecond / macOS-fenced PID-reuse defence (H4). Item 4 of this
runbook is the operations-side framing of H4; the security note is the posture
framing.

**See the INTD-012 evidence runbook for the Windows CI matrix shape.**
[`intd-012-windows-evidence.md`](./intd-012-windows-evidence.md) documents which
intercept crates are exercised on `windows-latest`, which `#[cfg(...)]` gates
run in the matrix, and the deliberate gaps the maintainers chose not to expand
in `v0.6.0-beta`. Item 5 of this runbook references that document for the
`main`-only trigger trade-off.

**Daemon-version skew is a future-tag concern, not a v1 one.** The `v0.6.0-beta`
cut is a single-version daemon: there is no rolling upgrade story, no peer
compatibility matrix across daemon versions, and no driver-version negotiation
that survives a daemon restart. An operator running `v0.6.0-beta` should run a
single tagged binary on a single user account and let the daemon's per-user
singleton invariant do the rest. Multi-version coexistence is out of scope here.

**Recovery from any fence-state corruption is documented in the demo runbook.**
`plans/specs/2026-04-26-rtai-demo-runbook.md` §3 (reset path) is the canonical
recovery sequence for both soft (between-demo) and hard (between-customer) state
resets. Operators handling `v0.6.0-beta` deployments should treat that section
as the source of truth for "how do I get back to a clean daemon state?"
