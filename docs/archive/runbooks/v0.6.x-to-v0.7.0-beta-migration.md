This note tells operators of an existing `v0.6.x` install what changes in
`v0.7.0-beta` and what they need to do — if anything — to upgrade. The release
theme is **daemon-working**: the protection claim is now verifiable on every
supported render surface from code state alone (see the release plan's
"daemon-working slate" section). Most of the surface delta is additive; the
items below call out the few places where operator action or expectation needs
to shift.

## TL;DR

- **No required config migration.** `v0.6.x` installs upgrade in place; existing
  `.anvilrc` files keep working untouched. An optional `anvil migrate` command
  rewrites them to the `v0.7.0-beta`-native `.anvil.<ext>` shape.
- **New in-tree tracked content.** Repos that use the v1 protection loop now
  write to `anvil/witness/` (active chain + archive + manifest). This directory
  is meant to be committed.
- **One new binary.** `anvil-run` ships as a separate executable for
  wrapped-launch ingress. Existing shell setups are unaffected unless you source
  `shell/anvil-run.sh`.
- **Hooks register under host managers automatically.** If you use lefthook,
  husky, or pre-commit-framework, `anvil start` integrates as a managed entry
  instead of overwriting `.git/hooks/`.
- **Exit codes for `anvil-run` are stabilised.** Shell wrappers can switch on
  `64 / 69 / 73 / 75 / 78`. See the [`anvil-run` manpage](../../runbooks/anvil-run.md) EXIT
  STATUS section.
- **No data migration.** Witness chains start fresh on adoption; existing
  baselines + identities carry forward unchanged.

## Upgrade

The upgrade path matches the install path you used originally:

```bash
brew upgrade eddacraft/tap/anvil           # Homebrew
winget upgrade --id eddacraft.anvil         # WinGet
scoop update anvil                          # Scoop
# Cargo: anvil and anvil-run ship as separate crates and need separate
# install invocations.
cargo install --git https://github.com/eddacraft/anvil-001 --tag v0.7.0-beta eddacraft-anvil --bin anvil
cargo install --git https://github.com/eddacraft/anvil-001 --tag v0.7.0-beta eddacraft-anvil-run --bin anvil-run
sh <(curl -fsSL https://anvil.dev/install)  # curl installer (Homebrew-aware)
```

The curl installer ([WATCHUX-001](../../../CHANGELOG.md)) already detects an
existing Homebrew-managed binary and prints the matching `brew upgrade` command
rather than overwriting it.

After upgrade, run `anvil status` once per active project to confirm the new
protection claim renders cleanly:

```bash
anvil status --json | jq '.claim.worktree_state'   # → "full"
```

(`anvil status --verify` is the activation diagnostic flow; the protection claim
is on the plain `anvil status --json` document under `.claim`. See the
[release runbook §3 pre-flight](../../runbooks/v0.7.0-beta-release-runbook.md#3-tag-time-hard-gate-protection-claim-renders-on-every-surface)
for the full cross-surface check.)

A `"full"` worktree state on every surface (CLI, doctor, MCP shim, TS driver)
means the daemon-working contract is honoured.

## What's new (and why you may notice)

### Witness chain (`anvil/witness/`) is now load-bearing

The in-tree, hash-chained witness file at `anvil/witness/active.ndjson` records
which protection layers fired on which commit. It travels with the repo via
`git worktree add`, `git clone`, and `git push`. The pre-push hook calls
`verify_chain_dag` across all witness segments before allowing the push; the L5
audit (`anvil audit-chain`) re-walks history to catch commits that bypassed
pre-commit / pre-push.

**Operator impact:**

- `anvil/witness/` is **tracked content** and should be committed.
  `.gitattributes` is pre-positioned by `anvil start` with `merge=union -text`
  so parallel branches never produce conflict markers.
- A teammate who commits with `--no-verify` or without `anvil` on PATH will land
  commits without witness lines. Recover with
  `anvil hook bootstrap --witness-recent`.
- The nightly L5 audit at `.github/workflows/anvil-audit.yml` is active by
  default. Disable by commenting out the `schedule:` block — don't delete the
  workflow.

Full operator surface, line shape, and failure-mode recovery in the
[witness-chain runbook](../../runbooks/anvil-witness-chain.md).

### Hook coexistence with lefthook / husky / pre-commit-framework

`anvil hook bootstrap` (and the `anvil start` install path) probes the repo root
for hook-manager marker files and registers Anvil as a managed entry instead of
overwriting `.git/hooks/`. Detection precedence:

1. `.husky/` → Husky
2. `lefthook.yml` / `lefthook.toml` / `lefthook.yaml` → Lefthook
3. `.pre-commit-config.yaml` → pre-commit framework
4. `.cargo-husky/hooks/` → cargo-husky (unsupported, falls back to Plain)
5. `core.hooksPath` set → CoreHooksPath (unsupported, falls back to Plain)
6. Nothing matched → Plain (`anvil` writes directly to `.git/hooks/`)

Lefthook and pre-commit framework require a one-time manual `extends:` or
`repos:` merge after install. Husky and Plain are fully automatic. Full
per-framework behaviour, install/uninstall round-trip guarantees, and
troubleshooting in the [hook coexistence runbook](../../runbooks/anvil-hook-coexistence.md).

**Operator impact:** if your repo already runs lefthook/husky/pre-commit, the
install no longer clobbers your `.git/hooks/`. Read the coexistence runbook
before adopting in a repo with non-default hook setup.

### `anvil-run`: new wrapped-launch ingress binary

`anvil-run` is a separate executable that wraps an agent process launch in an
Anvil-managed session — resolves context, queries the daemon, registers a
session, spawns in a process group, heartbeats, and unregisters on exit. It
ships alongside `anvil` and is reached through the shell-integration script at
`shell/anvil-run.sh`.

**Operator impact:** install picks it up automatically. To route `claude`,
`codex`, or `aider` through the launcher, source the script:

```bash
. "$(brew --prefix anvil)/share/anvil-run/anvil-run.sh"  # Homebrew
. "$HOME/.local/share/anvil/anvil-run.sh"                # curl installer
```

Stable exit codes (`64 / 69 / 73 / 75 / 78`), env propagation, trust model, and
shell-integration semantics are in the [`anvil-run` manpage](../../runbooks/anvil-run.md).

### `.anvil.<ext>` configuration alternative

The config discovery layer (MLP2-040) now prefers `.anvil.<ext>` —
`.anvil.yaml`, `.anvil.yml`, `.anvil.json`, `.anvil.toml` — over the legacy
`.anvilrc`. `anvil start --format <ext>` writes the chosen extension with the
embedded `format` field matching.

**Operator impact:** existing `.anvilrc` files keep working unchanged; the
legacy fallback is intact. To migrate at your convenience:

```bash
anvil migrate
```

This is **opt-in**. There is no deprecation timer in `v0.7.0-beta`.

### New CLI surfaces

| Command                                                    | What it does                                                                                      |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `anvil audit-chain`                                        | L5 audit — re-walks a branch's commits, reports any without a witness line.                       |
| `anvil hook bootstrap --witness-recent`                    | Retroactively witnesses commits in `@{u}..HEAD` that were not witnessed at commit time.           |
| `anvil intercept unblock --worktree <path>`                | Clear a worktree fence after the underlying incident is resolved.                                 |
| `anvil intercept unblock --acknowledge-cascade <worktree>` | Clear a `degraded:fence-cascade` rate-limited fence (MLP2-026).                                   |
| `anvil migrate`                                            | Bridge a legacy `.anvilrc` to a `.anvil.<ext>` file.                                              |
| `anvil insights`                                           | Local-only weekly summary derived from the witness chain.                                         |
| `anvil version --check`                                    | Advisory update check; honest install-method-aware recommendation.                                |
| `anvil l4-validate`                                        | Dedicated L4-policy validator (formerly fused with `anvil hook pre-push`).                        |
| `anvil mcp install --client <…>`                           | One-command MCP wrapper for Cursor / Claude Code.                                                 |
| `anvil-run hook register --tool <…>`                       | Side-channel session registration (INTL-007).                                                     |
| `anvil uninstall [--global]`                               | Clean removal of Anvil state. (`--global` also removes user-level state.)                         |
| `anvil baseline --new-identity`                            | Fork opt-out — mint fresh project UUID, record previous as `forked_from`.                         |
| `anvil baseline --refresh --accept-suspicious`             | Explicit ack required when a refresh would drop ≥75% of findings (adversarial-refresh detection). |

### New protection-claim render surfaces

The closed-set protection-claim vocabulary is now rendered on **every shipping
surface** for the daemon-working hard-gate:

- `anvil status --json` — nested under the top-level `claim` key in
  `schemas/anvil-status.v1.json`.
- `anvil doctor --json` — same `ProtectionClaim` content under the
  `protection_claim` key; byte-identical to the status `claim` value.
- MCP shim `validate_write` response — typed `Option<ProtectionClaim>` gated on
  `DaemonStatus::Available`.
- TypeScript driver-client mirror — `ProtectionClaim` parity-tested against the
  Rust fixture.

Any client reading `anvil status --json` against a `v0.6.x` daemon already saw
the schema; `v0.7.0-beta` extends it to the doctor / MCP / TS surfaces. The
shape is wire-additive — existing consumers do not break.

## Behavioural changes worth knowing

### Action commands require an authenticated session

`anvil status`, `anvil start`, and the licence-gated commands listed in
`crates/anvil-cli/src/feature_flags.rs:38-58` now exit with code 0 and a
structured `{"state":"authRequired","next":"anvil auth login"}` payload when the
operator session is missing or has been revoked. This is most commonly hit by
operators upgrading from `v0.6.x` whose refresh-token chain was reused on a
separate machine — the backend revokes the session family for security, and the
next CLI invocation surfaces the `authRequired` state.

Recovery is one command:

```bash
anvil auth login
```

After the device-code flow completes, re-run the original command. Scripts and
editor integrations that consume `--json` should branch on
`state == "authRequired"` and route the operator to `anvil auth login` without
treating the prior call as a failure (the non-zero exit code used in `v0.6.x`
was changed deliberately so wrappers don't conflate "auth needed" with "command
broken").

If `anvil auth login` itself fails (device-flow timeout, network error, clock
skew), it now returns a distinct non-zero exit code so the `authRequired` state
and a genuine login failure can be told apart. See PR
[#1822](https://github.com/eddacraft/anvil-001/pull/1822) /
[#1824](https://github.com/eddacraft/anvil-001/pull/1824).

### Pre-push hook is stricter

The pre-push hook now applies the full L4-policy pipeline:

- **Version floor** (`required_anvil_version`). A repo policy that pins an
  `anvil` floor refuses pushes from older binaries. Upgrade the binary; the line
  is `anvil: upgrade anvil — required floor <version>`.
- **Cutoff commit** (`cutoff_commit`). A baseline-ancestry walk refuses pushes
  that don't descend from the pinned cutoff. Hex-shape validation on the policy
  boundary rejects symbolic refs.
- **Time budget** (`PRE_PUSH_BUDGET = 2s`). On exceed, emits one
  `gate_evaluated` line with `partial=true` rather than blocking. Set the budget
  knob in `.anvil.<ext>` if your history routinely trips it.
- **Witness chain DAG verification**. Linear-chain breaks, sequence gaps,
  missing genesis anchors, and orphan-merge parents are all refused with
  diagnostic lines that map onto the recovery procedures in the
  [witness-chain runbook](../../runbooks/anvil-witness-chain.md).

A repo where pre-push starts refusing pushes after the upgrade most commonly has
unwitnessed commits from teammates who pushed without `anvil` on PATH. Run
`anvil hook bootstrap --witness-recent` on the branch tip and commit the
resulting witness file.

### Fence persistence is unchanged from `v0.6.0-beta`

Fences still persist across daemon restart by design. See
[`docs/runbooks/v0.6.0-beta-release-runbook.md`](v0.6.0-beta-release-runbook.md)
for the recovery procedure. New in `v0.7.0-beta`: the persisted state also
tracks the four-fence cascade window (`RateWindow::new(4, 60s)`), and clearing a
cascade requires `anvil intercept unblock --acknowledge-cascade <worktree>` so
an operator cannot accidentally un-fence a worktree that is rapid-cycling.

### YAML resource bounds enforced

`anvil-config::parse` now rejects YAML aliases outright (1 MiB pre-parse cap,
depth-32 post-parse cap). A `.anvil.yaml` that uses YAML anchors / aliases will
be refused. Quote-escape the symbols if you need them inside a string scalar;
otherwise rewrite without aliases.

### Air-gap guarantee unchanged

The no-network promise is carry-forward from `v0.6.0-beta` and remains unchanged
— every core protection command (`anvil start`, `anvil baseline`,
`anvil intercept ensure`, all `anvil hook` subcommands, `anvil audit`, the
witness writer, `anvil-run`) makes zero network calls. The
[air-gap runbook](../../runbooks/anvil-air-gapped.md) and
`crates/anvil-cli/tests/air_gapped.rs` Linux network-namespace harness enforce
this in CI. Telemetry and `anvil version --check` remain opt-in and off by
default.

## Multi-branch adoption (enterprise / monorepo)

If you adopt on multiple long-lived branches in parallel, each branch's first
`anvil start` / `anvil baseline` mints its own genesis anchor (`GENESIS-FRESH`
or `GENESIS-BASELINED`). The chains are individually valid but mutually unaware,
and the first cross-branch merge will fail with `OrphanMerge` — each side's
witness lines were written before the other's existed.

Recommended rollout:

1. Adopt on the default branch first (`anvil start`, commit, push).
2. Wait for every active feature branch to rebase from / merge in the default
   branch so the shared genesis is present everywhere.
3. Only then activate Anvil on each feature branch.

If the parallel-adoption case already happened, use the
[OrphanMerge recovery procedure](../../runbooks/anvil-witness-chain.md#3-orphanmerge-on-a-merge-line)
in the witness-chain runbook — there is nothing about it unique to migration.

## Downgrade

Downgrading to `v0.6.x` is supported on a clean repo (no committed
`anvil/witness/` lines from `v0.7.0-beta`-only writers). The witness chain shape
is forward-compatible — older binaries can read `v0.7.0-beta` lines but cannot
emit the merge-line / `rules_sha` / `cutoff_commit` extensions, so a
mixed-version team will accumulate chains with mixed feature density. The DAG
verifier (`verify_chain_dag`) accepts both shapes.

**Mixed-version teams** (some operators on `v0.6.x`, some on `v0.7.0-beta`) need
one additional warning: `anvil audit-chain --rescan` re-evaluates today's rules
against historical witness lines and uses `rules_sha` to detect drift. Lines
written by a `v0.6.x` binary lack `rules_sha` and will appear as drift in the
`--rescan` output. Either pin the entire team to the same version, or disable
`--rescan` (it is off by default; do not enable it during a mixed-version
window).

If you need to downgrade and your team has been pushing for more than a day on
`v0.7.0-beta`, either:

1. Stay on `v0.7.0-beta`. The release fixes far more than it changes.
2. Or coordinate the downgrade — every contributor pins the same version, then
   on each clone reset the witness state with:

   ```bash
   anvil uninstall    # removes anvil/witness/ and the hook installation
   anvil start        # re-initialises with a fresh GENESIS-FRESH anchor
   ```

   Pause the audit workflow until the rebuilt chain has accumulated enough
   history for `audit-chain --threshold` to be meaningful again.

   Do **not** remove `anvil/witness/` manually without re-anchoring — that
   leaves the next commit's pre-commit hook writing into a missing-genesis state
   and the chain becomes `UnknownGenesis` on next push.

There is no automated downgrade path; the recovery is manual.
