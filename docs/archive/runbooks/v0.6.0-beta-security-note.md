# v0.6.0-beta — release security note

**Date:** 2026-05-07 **Tag:** `v0.6.0-beta` **Owner:** Release council
**Status:** Operator-facing security note for the `v0.6.0-beta` cut

This note documents the four HIGH security trade-offs the release council's
security-analyst lens surfaced during the `v0.6.0-beta` review. Each item is
shipped behaviour, not a planning artefact; each one names the file and line
range an operator can audit. Companion document:
[`v0.6.0-beta-release-runbook.md`](./v0.6.0-beta-release-runbook.md) covers the
operations items the same review surfaced.

This note is not a vulnerability disclosure. It is a record of what the v1 trust
boundary buys an operator, what it explicitly does not buy, and which of the v1
mitigations are spec-only versus runtime-wired.

---

## Trust boundary, v1

The `v0.6.0-beta` daemon and driver framework run a same-UID, local-IPC trust
model. The boundary is enumerated here so the four HIGH items below can be read
against a shared baseline rather than a missing one.

**What v1 enforces:**

- **Owner-only Unix domain socket.** `crates/anvil-intercept/src/ipc.rs` refuses
  to bind unless the parent directory is mode `0700` and the socket itself is
  mode `0600`, both owned by the daemon's UID. A peer with a different UID
  cannot reach the listener. The directory `0700`/owner check is at
  `crates/anvil-intercept/src/ipc.rs:340-398` (`unix_perms::ensure_dir`) and
  `crates/anvil-intercept/src/ipc.rs:400-416` (`ensure_existing_dir`); the
  socket-file `0600`/owner check is at
  `crates/anvil-intercept/src/ipc.rs:418-434` (`ensure_socket_file`). The bind
  ladder that wires both together — including the post-`bind()` `fchmod` and
  `set_permissions(0o600)` that tighten the socket before any peer can connect —
  is `IpcListener::bind` at `crates/anvil-intercept/src/ipc.rs:520-602`.
- **Owner-only Windows named pipe with rejected remote clients.**
  `crates/anvil-intercept-win32/src/lib.rs:39-53` builds the pipe with an
  explicit owner-only DACL and sets `reject_remote_clients(true)` so the pipe is
  never reachable across hosts. The DACL grants `0x12019f` rather than
  `GENERIC_ALL` to preserve a same-user trust scope rather than open access.
- **Daemon-minted driver identity.** The daemon never trusts a `driverName`
  field for identity. `crates/anvil-intercept/src/fanout.rs:24-37` documents
  that `correlation.originating_driver_id` is computed from `SO_PEERCRED` /
  `GetNamedPipeClientProcessId`, not from the manifest — a same-UID peer
  declaring `"driverName": "vscode"` cannot impersonate the real VSCode driver
  in cross-session telemetry decisions.
- **Manifest-driven capability lattice.** Promotion from `Attached` to
  `Participating` (enforcement-acking) is a pure function of the request and the
  manifest: `crates/anvil-intercept/src/auth.rs::is_driver_allowed` gates
  promotion through a binary-path allowlist (`~/.config/anvil/drivers.allow`),
  and `DriverManifest::validate_workspace_roots` cross-checks claimed
  `workspaceRoots` against the live `SessionRecord` set. Stock LSP clients that
  omit `anvil/enforcement/ack` from their manifest get diagnostics for free but
  cannot promote — see `editor-and-mcp-driver-design.md` §2.3a.

**What v1 does not enforce:**

- No remote / cross-UID surface. There is no TCP listener, no auth token, no
  signed manifest, no OIDC. Cross-host attach is refused by the transport layer,
  not by application policy.
- No TLS. Local IPC only.
- No signed manifests. Driver identity in v1 is
  `(uid, canonicalised binary path)`; v2+ tightens this to a signed install-time
  token.

**What's NOT widened in this release:** no remote / cross-UID surface, no TLS,
no signed manifests.

## H1: allowlist file mode and owner not verified before read

**Surface:** `crates/anvil-intercept/src/auth.rs:197-209` documents the v1
contract; the read happens at `crates/anvil-intercept/src/auth.rs:227-267`.

**What ships.** `is_driver_allowed` opens the allowlist with
`fs::read_to_string` and parses each non-comment line as an absolute path,
canonicalises both sides, and returns `Ok(true)` only on equality. There is no
`lstat` of the allowlist itself — file mode and owning UID are not verified
before the read.

**Why this is a v1 trade-off.** The trust boundary (§ above) treats same-UID
peers as inside the daemon's circle of trust; the allowlist is owned by the same
UID as the daemon and lives under the operator's `$HOME`. The intended v1
posture is "if a same-UID attacker can already write your dotfiles, the
allowlist is not the first thing they would tamper with." That argument is
defensible for the v1 cut but is not a verifier — an operator who shares a
machine, an operator whose dotfiles are tracked in a permissive publicly-cloned
home directory, or an operator running under a CI account whose `$HOME` is
shared with other tooling all have legitimate reasons to want the file mode
pinned at read time.

**What an operator MUST do.** Manually set the allowlist to mode `0600` owned by
the daemon's UID before the daemon is allowed to consult it.
`chmod 0600 ~/.config/anvil/drivers.allow` is the minimum; on shared machines
also confirm the parent `~/.config/anvil/` directory is mode `0700` owned by the
same UID.

**What is tracked for the next tag.** `lstat` + owner-UID hardening on the
allowlist read path. The fix is a small change at the `read_to_string` site and
adds one syscall per promotion check; tracked outside this release so the v1
contract documented in `auth.rs:194-226` remains literal.

## H2: Cross-session telemetry redaction hash is unsalted SHA-256

**Surface:** `crates/anvil-intercept/src/fanout.rs:436-441`. The full redaction
pipeline is at `crates/anvil-intercept/src/fanout.rs:420-453`; the INTD-015
fan-out contract is at `crates/anvil-intercept/src/fanout.rs:1-100`.

**What ships.** `hash_of_path(input: &str)` returns
`format!("[redacted:{}]", hex_sha256(input))`. There is no per-startup salt, no
HMAC key, no separator between the rule context and the path. `redact_title` and
the rest of the redaction pipeline build on this same primitive.

**Why this matters.** The fan-out's `Delivery::Redact` arm exists for the case
where `telemetry.allow_cross_session` is set: a subscriber is permitted to see
that _some_ event happened in another session, but not _which file_. The
redaction is the visibility boundary. SHA-256 of a known-corpus path is a
one-shot precompute: a same-UID subscriber who can guess at the deployment's
repository tree (or who has a list of common paths `secrets.env`, `.env.local`,
`config/aws.json`) can build a rainbow table for `hash_of_path` and reverse a
`(rule_id, hashed_path)` pair to a plaintext path with no further interaction
with the daemon.

**Operator framing.** Treat `Delivery::Redact` as a **policy-compliance signal,
not a confidentiality boundary**. If the redacted form must be strong against
same-UID corpus precompute, do not enable `telemetry.allow_cross_session` in v1.
The default is `false` (`crates/anvil-intercept/src/fanout.rs:7-11`); leaving it
disabled is the documented safe posture.

**What is tracked for the next tag.** Per-startup HMAC salt minted on daemon
launch, with the salt rotated on every cold start so a subscriber captured
during one daemon lifetime cannot correlate against another. The contract change
is internal — subscribers do not need to update — and the `Delivery::Redact`
shape stays the same.

## H3: §4.4 daemon-side redaction filter is spec-only outside `validate_write`

**Surface:** the spec is at
`plans/specs/anvil-driver-framework/editor-and-mcp-driver-design.md:598-605`
("Implementation surface (v1) ... the runtime implementation is wired by the MCP
driver consumer (RMCPF-010 owns the filter integration)"). The one MCP tool that
_is_ wired through the redaction contract today is
`crates/anvil-cli/src/mcp/tools/validate_write.rs:374-424`; in particular
`normalise_response_diagnostics` masks secret-rule diagnostics at lines
`383-397`.

**What ships.** `anvil_validate_write` is the only MCP tool whose response
payload is rewritten by a redaction filter before it leaves the MCP transport.
The filter is invoked at
`crates/anvil-cli/src/mcp/tools/validate_write.rs:374-401` and uses
`redact_secret_values` (line 415-424) to mask anything matching the default
secret patterns. Other MCP tool surfaces — `scan.files`, `fix.apply`,
`status.query` — go through the MCP transport without this filter.

**Why this matters.** The spec at `editor-and-mcp-driver-design.md:562-606`
specifies a daemon-side default-deny redaction contract spanning **all three**
of those payloads: secret-detection content excerpts get masked to
`<<redacted: secret>>`, absolute filesystem paths get rewritten to
workspace-relative, `fix.apply` diff payloads get pre/post excerpts masked. In
`v0.6.0-beta`, that contract is shipped as **specification only**. The runtime
filter integration is owned by RMCPF-010 and lands in a later tag. An operator
reading the spec and assuming it is wired today would be wrong for everything
other than `validate_write`.

**Operator framing.** Treat the v1 MCP transport as carrying **un-redacted
absolute paths** for `scan.files`, `fix.apply`, and `status.query` responses,
and **un-redacted secret-rule excerpts** for the same tools' content fields.
Same-UID trust (§ above) still applies — the MCP transport itself is reachable
only by same-UID peers — but a same-UID MCP client that an operator does not
fully trust (a third-party agent, an installed skill that runs subprocesses)
sees that material verbatim. If that posture is unacceptable for a deployment,
do not install third-party MCP clients into the v1 cut; the wired filter ships
in the next tag with RMCPF-010.

**What is tracked for the next tag.** RMCPF-010 wires the v1 redaction contract
for `scan.files`, `fix.apply`, and `status.query` against the daemon's MCP
transport. The spec at `editor-and-mcp-driver-design.md:562-606` is the binding
contract; v1 ships the spec, RMCPF-010 ships the runtime parity.

## H4: Linux PID-reuse defence has TOCTOU; macOS interrupt ladder fences-only

**Surface:** `crates/anvil-intercept/src/interrupt.rs:407-432` is the
`current_process_start_time` helper; the ladder caller is `run_unix_ladder` at
lines `200-284`; the AD-7 fence-on-failure invariant is documented at lines
`26-43`. Peer-credential validation lives in
`crates/anvil-intercept/src/ipc.rs::validate_connected_peer_for_client` —
**Linux and macOS are at parity** as of issue #1327's resolution, so this entry
is narrowed to the interrupt ladder only.

**What ships.** On Linux, the ladder reads `/proc/PID/stat` field 22 (starttime)
at lines `408-418` and compares against the registry's `record.started_at_unix`
value before invoking `kill()` on the leader and `killpg()` on the process
group. Between the `read_to_string` of `/proc/PID/stat` (line `410-415`) and the
actual `kill()` call (line `233`, `253`, `273`) there is a microsecond-scale
TOCTOU window: the target PID could exit and be reused by an unrelated process
between the starttime read and the signal. On macOS, the helper at lines
`419-431` returns `None` unconditionally — `proc_pidinfo` is **not yet
implemented** for the macOS branch. The PID-reuse defence falls through to
`verify_leader` returning the conservative `Err(reason)` path, which under AD-7
means **the macOS interrupt ladder always fences rather than signalling** when
start-time data is required.

**What is at parity on macOS.** The IPC trust boundary itself (peer-credential
validation) **is** at Linux parity on macOS as of issue #1327: Linux uses
`SO_PEERCRED` via `getsockopt`, macOS uses `getpeereid(2)` via
`nix::unistd::getpeereid`, both return the peer's effective uid and the daemon
rejects any connection whose `peer_uid != current_uid` with the same
`IpcError::SocketPeerPermissions` variant. The macOS gap documented in this
entry is now narrowly the interrupt ladder's start-time read, not the wider
trust boundary.

**Why this is the right v1 trade-off.** AD-7 makes one rule absolute: any
signal-delivery uncertainty ends in a fence, immediately. The Linux TOCTOU
window is real but its blast radius is bounded — if a wrong-target signal is
delivered, the `Err` from the unexpected `kill()` outcome (or the follow-up
liveness check at line `294-297`) trips `InterruptOutcome::FenceImmediately`,
the worktree fences, and the operator sees an explicit unblock requirement
rather than a silent mis-targeting. The fence is the safety primitive, not the
signal itself.

**Operator framing on Linux.** A wrong-target signal **does not result in a
wrong-process kill being treated as success.** The fence-on-failure invariant
means the worktree ends fenced and the operator's recovery is explicit
(`anvil intercept unblock --worktree`). The TOCTOU window is documented here so
an operator reading interrupt telemetry can recognise the pattern: occasional
fences with `SignalDeliveryFailed` reason, no collateral damage outside Anvil's
own session state.

**Operator framing on macOS.** The **interrupt ladder** is effectively
Linux-only in v1. macOS deployments degrade to fence-on-uncertainty: the
PID-reuse defence cannot run, so the conservative path is taken on every
interrupt. Operators see fences instead of signals; recovery is the same
explicit unblock. This is expected v1 behaviour, documented at lines `419-431`
of `interrupt.rs`. Peer-credential validation, by contrast, is fully wired on
macOS — the daemon's same-UID trust boundary holds identically on both
platforms.

**What is tracked for the next tag.** macOS `proc_pidinfo`-backed start-time
read so the PID-reuse defence runs on macOS the way it runs on Linux. The Linux
TOCTOU window is intrinsic to the `/proc/PID/stat` + `kill()` shape and is not
closed in any planned tag — the AD-7 fence-on-failure invariant is the
documented mitigation.

## What's NOT widened in this release

No remote / cross-UID surface. No TLS. No signed manifests. The v1 trust
boundary is local, same-UID, and manifest-driven — the four items above are HIGH
because they are real trade-offs inside that boundary, not because the boundary
itself moves in `v0.6.0-beta`.
